## 一、问题定义(量化)

### 1.1 物理尺寸现实

800×450 逻辑画布经 `Scale.FIT` 投到手机上,1 game px 的物理大小:

| 设备 | 缩放系数 | 1 game px ≈ | 28px 高按钮 ≈ | 44pt 触摸标准需要 |
|------|---------|------------|--------------|------------------|
| iPhone SE (667×375) | 0.83 | 0.17 mm | 4.8 mm | **~41 game px** |
| iPhone 13 (844×390) | 0.87 | 0.16 mm | 4.5 mm | ~43 game px |
| 桌面 1080p 窗口 | ≥1.5 | 0.4+ mm | 11+ mm | 无压力 |

Apple HIG 44pt ≈ 7mm、Material 48dp ≈ 8mm。**当前主按钮(高 28-40 game px)在手机上是 4.5-6.8mm,商店购买按钮(高 16)只有 2.7mm** ——视觉上就是"按不准的小点",即使热区已扩到 52px,玩家的心理预期仍由视觉尺寸决定。

### 1.2 根因

所有 UI 尺寸按 PC 鼠标精度设计(密度高、元素小),FIT 等比缩放把 PC 密度原样压进 6 英寸屏。**适配的本质不是缩放,是密度交换:移动端必须用「更少的同屏信息」换「更大的单元素尺寸」。** 空间从三处来:折叠次要信息、滚动/分页、图标化文字按钮。

### 1.3 现状资产与约束(代码层)

- ✅ 已有地基:`TextFactory` 单点文字(textScale 钩子)、`isTouchDevice()`、`attachPressInteraction`(信息可后置到长按)、Panel 触摸滚动、安全区
- ⚠️ 约束:**332 处 `GAME_WIDTH/GAME_HEIGHT` 绝对坐标(32 个文件)**,场景布局全部硬编码;46 个 Button 调用点;地图容器可拖拽但无缩放
- ⚠️ 不能用的捷径:给场景根容器整体 `setScale(1.3)` 等效裁掉 26% 视野(边缘出画),且热区/相机坐标全要补偿——不可行

## 二、候选方案

### 方案一:UI 设计令牌 + 场景移动布局档(推荐)

保持 800×450 + FIT 不变。新增 `Layout` 设计令牌模块,**共享组件按 `uiScale`(移动 1.3)真实放大视觉尺寸**;6 个高密度场景增加"紧凑布局档"(`Layout.isCompact` 分支),用折叠/滚动/图标化腾出空间。

```ts
// src/ui/Layout.ts(核心 API 草图)
export const Layout = {
  /** 视觉缩放:移动 1.3,桌面 1.0;可被设置页覆盖(自动/标准/大/特大) */
  factor: resolveUiScale(),            // isTouchDevice() ? 1.3 : 1.0
  s(v: number): number { return Math.round(v * Layout.factor); },
  /** 布局分支开关:紧凑(移动)布局 vs 桌面布局 */
  get isCompact(): boolean { return Layout.factor > 1.15; },
  /** 最小触摸目标(热区,已有)与最小视觉目标(新) */
  minHit: 52,
  minVisual: 36,
};
```

- **textScale 与 uiScale 合并**:现有 textScale(1/1.25/1.5)升级为统一 `uiScale`,文字随 UI 同步缩放,避免两套缩放打架(设置页一个「界面大小」选项,旧存档 textScale 迁移)。
- 组件消费:`Button`(width/height 过 `s()`)、`Panel`(行高/标题/关闭钮)、`SkillBar`(槽 44→s(44)=57)、`UltimateBar`、`BattleHUD`、弹窗。
- 场景档:见 §三。

| 维度 | 评估 |
|------|------|
| 工作量 | **5-8 天**(阶段化,每步可独立上线) |
| 风险 | 低——桌面路径 `factor=1` 完全不变;移动分支增量添加 |
| 效果 | 移动端主按钮 36-57 game px(6-9.7mm),达标 |
| 局限 | 800×450 内放大 1.3 倍必须删减密度,信息组织有取舍 |

### 方案二:移动端独立逻辑分辨率(如 640×360)

移动设备启动时用更小的逻辑画布,FIT 后所有内容物理放大 25%。

**不推荐,数学上是劣化版方案一**:整体放大 1.25 的同时逻辑空间缩小到 640×360,同屏内容必须减少——密度问题一点没少,却引入了"两套坐标系"(332 处绝对坐标在两种分辨率下语义不同),且无法按元素差异化(战场单位不需要放大,UI 需要)。唯一优点是单位/特效也变大,但像素风单位 2-3 倍缩放本就清晰。

| 维度 | 评估 |
|------|------|
| 工作量 | 3-4 天改造 + 长期双分辨率维护税 |
| 风险 | 高——所有硬编码坐标双义,测试矩阵翻倍 |

### 方案三:Scale.RESIZE + 屏幕空间 UI(终极形态)

画布 = 设备真实分辨率;战场经世界相机 `zoom = min(w/800, h/450)` 渲染;UI 全部迁移到独立 UIScene,以锚点(左上/右下/居中)+ 真实像素布局,彻底摆脱 800×450 束缚。黑边消失(背景延伸),UI 元素任意设备上都是真实 44px+。

| 维度 | 评估 |
|------|------|
| 工作量 | **2-3 周**——332 处坐标全部迁移、每个 UI 组件改锚点制、双相机输入路由、全场景回归 |
| 风险 | 高——一次性大手术,期间主干不可发布 |
| 效果 | 最佳;也是后续支持平板/折叠屏/竖屏模式的唯一通路 |

### 决策矩阵

| | 方案一 令牌+布局档 | 方案二 双分辨率 | 方案三 RESIZE |
|---|---|---|---|
| 移动端视觉达标 | ✅ 36-57px | ⚠️ 等比 1.25 | ✅ 真实像素 |
| 桌面零回归 | ✅ factor=1 | ❌ 仍单路径 | ⚠️ 全量回归 |
| 可渐进交付 | ✅ 按场景 | ❌ 一次切换 | ❌ 一次切换 |
| 长期演进 | ✅ 是方案三的前置(令牌先行) | ❌ 死路 | ✅ 终点 |
| 工作量 | 5-8 天 | 3-4 天+维护税 | 2-3 周 |

**推荐:方案一**,且其令牌层是将来升级方案三的必经之路(组件先令牌化,再换坐标系),投入不浪费。

## 三、推荐方案详细设计(方案一)

### 3.1 基础设施(阶段 1)

1. **`src/ui/Layout.ts`** — 如上 API。`resolveUiScale()` 优先级:用户设置 > 触摸设备默认 1.3 > 1.0。
2. **设置页**:「文字大小」改为「界面大小」:自动 / 标准(1.0) / 大(1.3) / 特大(1.5);`AccessibilitySettings.textScale` 字段迁移为 `uiScale`(`?? textScale ?? 默认` 兼容旧存档)。
3. **共享组件令牌化**(46 个 Button 调用点不动,组件内部消费):
   - `Button`:构造的 width/height 内部过 `s()`;字号已随 textScale。
   - `Panel`:标题栏 24→s(24)、行高、滚动条宽、关闭按钮 s(28)。
   - `SkillBar`:`SLOT_SIZE = Layout.s(44)`(57px ≈ 9.7mm)、间距 s(4);8 槽总宽 484px 仍在画布内。
   - `UltimateBar`:BUTTON_SIZE s(36)=47。
   - 弹窗(HeroDetailPopup 等):宽高朝全屏靠(`min(POPUP_W*1.15, GAME_W-16)`),行高已测高自适应。

### 3.2 场景紧凑布局档(阶段 2,`Layout.isCompact` 分支)

空间腾挪三原则:**次要信息折叠进长按/弹窗、列表改滚动、文字按钮图标化**。

| 场景 | 桌面(不变) | 移动紧凑档 |
|------|-----------|-----------|
| **MainMenu** | 6 按钮 160×28 | 按钮 s()→208×36;右上音乐/音效/设置改 36×36 图标钮;底部统计/版本合并一行 |
| **HeroDraft** | 26 卡 5 列网格 | 卡片 72×118→94×142(放大 1.3),改横向翻页(每页 8 张,页码圆点)或 Panel 纵向滚动;卡面只留名字+定位色条+2 属性,其余信息长按详情(已有) |
| **Map** | 全图静置 | `mapContainer.setScale(1.3)` + 既有拖拽平移(节点 22→29px ≈ 5mm);顶栏「英雄/遗物/进度」并入 [概览];阵型按钮 s() |
| **Battle** | 左右单位列表+技能栏 | 技能槽 57px;左右单位列表折叠为**头像血条窄条**(点击展开浮层);顶部战斗类型/Act 描述/金币合并一行;速度/暂停/概览/威胁线改 40×40 图标钮纵列右缘 |
| **Shop** | 6 卡 3×2 | 2 列 + Panel 滚动,卡片放大 1.3;购买按钮 60×22→s()=78×29;属性对比保留(核心决策信息) |
| **Event/Rest/Reward** | 现状 | 套 s() 即可(按钮本就居中大块);Reward 统计表行高 s() |

### 3.3 空间预算验算(以 Battle 为例)

- 技能槽 8×57+7×5 = 491px < 800 ✅
- 头像条:8 单位 × s(22)=29px 高,纵向 232px < 战场区高 ✅
- 图标钮列:4 × 40 + 间距 = 192px 贴右缘,不与战场重叠 ✅

### 3.4 验收标准

1. 移动端(667×375 实机/模拟):所有可点元素**视觉**高度 ≥36 game px(≈6mm),主操作 ≥44;无文字溢出/遮挡
2. 桌面 `factor=1.0` 像素级回归(截图 diff)
3. 设置页四档实时切换,旧存档 textScale 正确迁移
4. `tsc` + 全测试 + 双端 Playwright E2E(桌面上下文 + hasTouch 上下文)通过

### 3.5 路线图与工作量

| 阶段 | 内容 | 估时 |

| 1 | Layout.ts + 设置迁移 + 5 个共享组件令牌化 | 1.5-2 天 |
| 2a | Battle + HeroDraft(最高价值) | 2 天 |
| 2b | Map + Shop + MainMenu + 杂项场景 | 1.5-2 天 |

### 3.6 风险与缓解

| 风险 | 缓解 |
|------|------|
| 1.3 倍后个别布局仍溢出 | 沿用 v1.26.0 的测高推进/scale-clamp 模式;E2E 截图全扫 |
